# Downstream doors — where the archaeology may matter

Status: **boundary map; no downstream adoption authorized by this document**

The purpose of this file is to make promising crossings visible without silently walking through them.

## Door 1 — Corpus OS: entrusted execution

### Existing evidence

Corpus OS already distinguishes Trust admission from Session execution through a one-shot Action Warrant and terminal receipt path.

### Possible extraction

Treat the current Trust Runtime as one executable specimen of **entrusted authority**, then ask whether its declarations need to express more of:

- originating authority;
- exact corpus subject;
- declared purpose;
- powers granted and withheld;
- delegation limits;
- evidence obligations;
- review/challenge authority;
- expiry/exhaustion;
- succession.

### Boundary

Do not rename existing fields to match trust-law nouns unless the semantics actually change. Preserve `legalValidity: unclaimed` unless and until a separate legal process establishes something stronger.

## Door 2 — Project0: constituted corpus identity

### Possible extraction

Project0's adopted-root and lawful-reachability work may provide the deeper identity layer for a corpus that survives changing projections and operators.

Questions:

- What constitutes the corpus?
- Which representation is currently authoritative?
- How is a successor projection constituted?
- Can an unauthorized but genealogically valid fork remain explicitly non-authoritative without denying its existence?

### Boundary

Do not let “entrusted corpus” create a second canonical identity law. Any mapping must reuse or extend Project0's existing constitution/reachability primitives rather than bypass them.

## Door 3 — TranchNode: continuity through transformation

### Possible extraction

TranchNode can test whether a corpus can remain reconstructibly itself while:

- storage changes;
- representation changes;
- custodians change;
- authority changes hands;
- some nodes disappear;
- new authorized projections are constituted.

The key question is not merely whether bytes survive. It is whether continuity evidence can survive transformation without smuggling authority from one projection to another.

## Door 4 — Conservation of Authority

### Existing convergence

The Collective already treats some authority as consumable: one admitted act should not be replayed into multiple consequences merely because its representation was copied.

### Trust-archaeology question

Does historical fiduciary practice reveal useful distinctions among:

- standing office/power;
- one-shot authority;
- delegated power;
- exhausted authority;
- suspended authority;
- removed authority;
- successor authority?

The answer could sharpen the architecture, but historical resemblance must not substitute for executable requirements.

## Door 5 — Refusal Topology

Entrusted systems have meaningful negative space.

Examples:

- technically possible but unauthorized;
- authorized in role but outside purpose;
- authorized but insufficiently witnessed;
- once authorized but now exhausted;
- attempted during a succession gap;
- refused by one layer after authority was already spent at another.

These refusals may describe the actual shape of the constitution more accurately than a role matrix.

## Door 6 — GitHub and project continuity

### Hypothesis

A GitHub repository can be treated as a **projection/custody surface** rather than the sovereign identity of a durable project.

A future continuity packet could contain enough evidence to answer:

```text
What corpus is this?
What adopted root/history constitutes it?
Why is this repository currently authorized to project it?
Who may administer this projection, in what capacity?
What happens if GitHub or the current administrator disappears?
Where is the successor path declared?
```

### Boundary

Open-source licenses, GitHub account ownership, copyright, trademark, contractual rights, and legal trust ownership are separate questions. Architecture cannot manufacture any of them.

## Door 7 — future human legal consultation

A later legal conversation can use this archaeology as a question generator, not as an answer key.

Useful questions for qualified counsel / the user's trust consultant may eventually include:

- Which Static Collective assets could actually be held by a trust or other entity?
- Which assets should not be?
- Who should hold copyright, trademarks, domains, repository administration, signing keys, recordings, and physical property?
- How should licensing obligations survive a transfer?
- What powers should a trustee, manager, protector, contributor, or successor actually have?
- What jurisdiction, tax, reporting, fiduciary, and succession consequences follow?
- How should off-chain/off-platform legal authority be evidenced to software without pretending the software itself creates legal validity?

No answer is proposed here.

## Door 8 — cross-project stewardship membrane

The largest architectural possibility is a project-independent membrane:

```text
constituted corpus
    -> declared purpose
    -> entrusted capacities
    -> bounded powers
    -> admission
    -> consequence
    -> receipt
    -> review / refusal topology
    -> succession
```

This should **not** be built as a shared framework yet.

Graduation gate:

1. Corpus OS demonstrates a materially useful entrusted-authority case.
2. A second, substantially different project demonstrates the same invariant without importing Corpus-specific semantics.
3. Succession or projection migration is exercised as a real specimen.
4. The shared residue is smaller and clearer than the two local implementations.

Until then, National Treasure keeps the map and GitBook keeps the incubating constellation.
